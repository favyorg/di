`GenModule` creates a module from a synchronous generator. Each `yield* Dependency` retrieves a service from the current DI context and adds its requirements to the inferred dependency contract. The generator's final `return` becomes the module's result.

Use `Tag<Service>()(name)` to declare a service contract independently of its implementation. A consumer can `yield*` the tag without importing a concrete provider or inheriting that provider's dependencies.

You can use `GenModule` alongside ordinary [`Module`](/module/module/) callables. Both use the same provider resolution, caching, and `.provide()` behavior.

## What `yield*` does

When `Main` executes `const user = yield* User`, the runner looks up the `User` key in the current context. A supplied module provider is resolved through DI; a supplied service object is returned directly. The generator resumes with that value, and `user` has the service type declared by the tag.

The tag declares a requirement. The composition root selects and prepares its implementation:

```ts
void Main({
  User: UserImpl.provide({ api }),
  Orders: OrdersImpl.provide({ api }),
}).Run();
```

Leaving out `User` or `Orders` is a TypeScript error. Neither a tag nor `yield*` installs a default implementation. `GenModule<Deps>()(User, callback)` checks that the generator returns a compatible service and creates a provider named `User`; it does not register that provider anywhere.

Fully bind an implementation's dependencies with `.provide()` before supplying it for a tag. `Main` knows nothing about `api`, so the type system does not infer a flat graph from `Main({ api, User: UserImpl, ... })`. A compatible service object also works, for example `User: { Load: async () => ({ id: 1, name: 'Alex' }) }`.

Tags use their declared `PropertyKey` as identity. Two tags named `'User'` address the same context entry, even if they are different objects; TypeScript cannot detect incompatible contracts declared separately under the same key. Export and reuse one tag for each service, or use distinct symbol keys when services need separate identities. The string key `'Module'` is reserved for built-in module metadata, so `Tag` rejects it. Tags have no call signature or `.provide()` method: dependency binding belongs to the implementation.

Requirements include every statically possible yield. A conditional branch can leave a provider unused at runtime, but its dependency remains part of the caller's contract. With the default lazy resolution, an unused provider is not executed.

## Explicit inputs and `Live`

Implementations can declare raw inputs with `GenModule<Deps>()`. In the example, `UserImpl` and `OrdersImpl` accept `{ api: Api }` through their callback arguments. A module may combine these explicit inputs with dependencies requested through `yield*`; its own contract includes both.

Declare each tag or module's dependency type directly below it:

```ts
export type MainLive = typeof Main.Live;
```

`typeof User.Live` contains only `{ User: UserService }`, where `UserService` is the type passed to `Tag`. `typeof UserImpl.Live` also carries the implementation's `api` requirement. `MainLive` contains `Main`'s result and its `User` and `Orders` requirements, just like an ordinary module's `Live` type. These types also work when an ordinary `Module` consumes a service. Reading `.Live` at runtime throws; it is a type-only marker.

## Bind dependencies with `.provide()`

You can replace the final startup line in `app.ts` with a bound module:

```ts
const ReadyMain = Main.provide({
  User: UserImpl.provide({ api }),
  Orders: OrdersImpl.provide({ api }),
});
type ReadyMainLive = typeof ReadyMain.Live;

void ReadyMain().Run(); // Alex, 1
```

Each `.provide()` returns an independent callable and removes the supplied keys from the remaining requirements. The iterable protocol is preserved, so another generator can use `yield* ReadyMain`. That consumer then requires an implementation under `Main`, the original declared name; the bound `User` and `Orders` keys are no longer required.

See [Partial Application](/module/partial/) for binding precedence and replacement rules.

## Yielding a concrete module

Tags are optional. You can still create a module with a name and yield the module itself:

```ts
const UserImpl = GenModule<{ api: Api }>()('User', function* ({ api }) {
  return { Load: async () => api.getUser() };
});
type UserImplLive = typeof UserImpl.Live;

const Main = GenModule()('Main', function* () {
  const user = yield* UserImpl;
  return { Run: () => user.Load() };
});
type MainLive = typeof Main.Live;

void Main({ api, User: UserImpl }).Run();
```

In this form, `Main` imports the implementation and inherits its transitive `api` requirement. The root still supplies the provider under `User`. Choose a tag when consumers should depend only on a service contract.

## Async work and errors

Use a synchronous `function*` to construct services, then perform asynchronous work in their methods. In the example, `Main(...)` synchronously returns `{ Run }`, while `Run()` awaits `User.Load()` and `Orders.Load()`.

The runner does not execute `async function*` callbacks or await yielded promises. A generator may return a promise as its final result; the caller then receives that promise. This extension does not add cancellation or resource scopes.

If resolving a dependency at `yield*` throws, the runner throws that error back into the generator. A surrounding `try/catch` can select a fallback, and `finally` runs during propagation. With `lazy: false`, failures during eager initialization happen before the generator starts and must be caught around the module call. Errors or rejections from a later async method call must be handled around that method call.

## Factories, caching, and interoperability

Use `makeGenModule` to create an independent generator factory:

```ts
import { makeGenModule } from '@favy/di';

const CachedGenModule = makeGenModule({ cache: 'module' });
// Create modules with CachedGenModule<Deps>()(nameOrTag, function* (...) { ... }).

CachedGenModule.flushCache();
```

The defaults are `cache: 'run'` and `lazy: true`. [Caching](/module/cache/) and [Lazy resolution](/module/lazy/) describe the same lifecycle rules used by generator modules. `flushCache()` clears only that factory's module cache. Input and output transforms are fixed by the extension; the options configure `cache` and `lazy`.

Tags can be used across generator factories, and modules from different generator factories can yield one another. Ordinary modules can consume a tag contract through `typeof TagName.Live` or a generator provider through `typeof Provider.Live`. Ordinary providers can supply a tagged service when their result is compatible and their requirements are fully bound. Ordinary `Module` callables have no iterable protocol, so they cannot themselves appear after `yield*`.

| Feature | `Module` | `GenModule` |
| --- | --- | --- |
| Callback | Ordinary function | Synchronous generator |
| Service access | Callback dependency object | `yield* Tag` or `yield* GenModule` |
| Dependency types | Explicit contract, often composed from `Live` | Explicit raw inputs plus inferred tag or module requirements |
| Async service methods | Supported | Supported |
| Root wiring, `.provide()`, caching | Shared DI behavior | Shared DI behavior |

For the exported signatures, see [`Tag`](/reference/api/#tag), [`GenModule`](/reference/api/#genmodule), and [`TGenModule`](/reference/api/#tgenmodulek-d-r-c--d). For the extension mechanism behind generator modules, see [Transform Output](/module/transform-output/#infer-dependencies-with-generators).
