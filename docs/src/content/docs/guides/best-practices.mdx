## Organize Around Focused Modules

Prefer one exported module per file when it represents a meaningful application capability. Export its `Live` type beside it so consumers can declare the dependency without repeating its return type.

<Editor client:load code={`// logger.ts
import { Module, type Live } from '@favy/di';

export interface LoggerService {
  info: (message: string) => void;
  error: (message: string) => void;
}

export const Logger = Module()(
  'Logger',
  (): LoggerService => ({
    info: (message) => console.log('[INFO]', message),
    error: (message) => console.error('[ERROR]', message),
  }),
);

export type LoggerLive = Live<typeof Logger>;`} />

Small modules are easier to replace, but avoid splitting code merely to increase the module count. A useful module owns one responsibility and exposes a stable return value.

## Keep Dependency Boundaries Explicit

Use interfaces for infrastructure or application ports. Use `Live<typeof Module>` when another module depends on a concrete module in the graph.

<Editor client:load code={`import { Module, type Live } from '@favy/di';

interface User {
  id: number;
  name: string;
}

const Database = Module<{ connectionName: string }>()(
  'Database',
  ({ connectionName }) => ({
    findUser: async (id: number): Promise<User> => ({
      id,
      name: connectionName + '-user-' + id,
    }),
  }),
);
type DatabaseLive = Live<typeof Database>;

const UserRepository = Module<DatabaseLive>()(
  'UserRepository',
  ({ Database }) => ({
    findById: (id: number) => Database.findUser(id),
  }),
);
type UserRepositoryLive = Live<typeof UserRepository>;

const UserService = Module<UserRepositoryLive>()(
  'UserService',
  ({ UserRepository }) => ({
    getDisplayName: async (id: number) => {
      const user = await UserRepository.findById(id);
      return user.name;
    },
  }),
);

const service = UserService({
  connectionName: 'primary',
  Database,
  UserRepository,
});

void service.getDisplayName(1);`} />

Keep dependency flow in one direction, for example infrastructure → repositories → services → entry points. A cycle makes initialization order and replacement boundaries difficult to reason about; extract the shared capability behind a lower-level interface instead. If resolution reads a provider key that is already being resolved, the runtime stops and throws `Circular dependency: <key>`.

Root calls and `.provide()` accept any non-null object as a dependency map, including class instances and custom-prototype objects. Only own keys participate in resolution, so initialize dependency fields on the instance itself instead of relying on inherited properties.

## Match Cache Lifetime to the Composition Root

### `run`: One Top-Level Call

The default `cache: 'run'` reuses dependencies during one top-level module call. It acts like request-scoped state only when the application invokes its composition root once per request:

<Editor client:load code={`import { Module, type Live } from '@favy/di';

const RequestContext = Module<{ requestId: string }>()(
  'RequestContext',
  ({ requestId }) => ({
    id: requestId,
    startedAt: Date.now(),
  }),
);
type RequestContextLive = Live<typeof RequestContext>;

const RequestHandler = Module<RequestContextLive>()(
  'RequestHandler',
  ({ RequestContext }) => ({
    handle: () => ({
      requestId: RequestContext.id,
      startedAt: RequestContext.startedAt,
    }),
  }),
);

export const handleRequest = (requestId: string) =>
  RequestHandler({ requestId, RequestContext }).handle();`} />

Calling `RequestHandler` twice creates two runs. @favy/di does not infer an HTTP request boundary on its own.

### `module`: One Factory-Wide Cache

Use `cache: 'module'` for values that should survive top-level calls made through the same `makeModule` factory:

<Editor client:load code={`import { makeModule } from '@favy/di';

const InfrastructureModule = makeModule({ cache: 'module' });

let poolCreationCount = 0;
const DatabasePool = InfrastructureModule()('DatabasePool', () => {
  poolCreationCount += 1;
  return {
    query: async (statement: string) => ({
      statement,
      rows: [] as string[],
    }),
  };
});

const firstPool = DatabasePool();
const secondPool = DatabasePool();

console.log(firstPool === secondPool); // true
console.log(poolCreationCount); // 1

InfrastructureModule.flushCache();`} />

Own cleanup explicitly: `flushCache()` removes cached values but does not call resource-specific disposal methods.

Use `cache: 'none'` when every dependency access must recompute. See [Caching](/module/cache/) for comparisons.

## Handle Errors Where They Can Be Recovered

Catch operational errors inside the async method or application boundary that can add context or convert them into a domain result:

<Editor client:load code={`import { Module } from '@favy/di';

interface User {
  id: number;
  name: string;
}

interface UserRepositoryPort {
  findById: (id: number) => Promise<User | undefined>;
}

type Result<T> = { ok: true; value: T } | { ok: false; error: Error };

const UserService = Module<{
  UserRepository: UserRepositoryPort;
}>()('UserService', ({ UserRepository }) => ({
  getUser: async (id: number): Promise<Result<User>> => {
    try {
      const user = await UserRepository.findById(id);
      if (!user) {
        return {
          ok: false,
          error: new Error('User not found: ' + id),
        };
      }
      return { ok: true, value: user };
    } catch (error: unknown) {
      return {
        ok: false,
        error:
          error instanceof Error
            ? error
            : new Error('Unknown repository error'),
      };
    }
  },
}));`} />

`transformOutput` receives a value after the module body returns. It can validate or wrap successful values, but it cannot catch an exception already thrown by the module body, and it does not await a rejected promise automatically.

## Build Test Helpers Around Instance State

Keep observations in the object returned by a mock factory. Do not attach per-test arrays to the factory function itself:

<Editor client:load code={`import { Module } from '@favy/di';

interface LoggerPort {
  info: (message: string) => void;
  error: (message: string) => void;
}

const Audit = Module<{ Logger: LoggerPort }>()('Audit', ({ Logger }) => ({
  recordLogin: (userId: number) => {
    Logger.info('login:' + userId);
  },
}));

const createMockLogger = () => {
  const logs: string[] = [];
  const errors: string[] = [];

  return {
    logs,
    errors,
    info: (message: string) => {
      logs.push(message);
    },
    error: (message: string) => {
      errors.push(message);
    },
  };
};

const mockLogger = createMockLogger();
Audit({ Logger: mockLogger }).recordLogin(7);

console.log(mockLogger.logs); // ['login:7']`} />

For complete unit and integration examples, see [Testing](/guides/testing/).

## Preserve Conditional Lazy Access

Parameter destructuring reads a dependency before the function body can evaluate a condition. Keep the dependency object and access the property inside the branch:

<Editor client:load code={`import { Module, type Live } from '@favy/di';

let initializationCount = 0;
const ExpensiveFeature = Module()('ExpensiveFeature', () => {
  initializationCount += 1;
  return {
    run: () => 'expensive result',
  };
});
type ExpensiveFeatureLive = Live<typeof ExpensiveFeature>;

const App = Module<ExpensiveFeatureLive>()('App', ($) => ({
  run: (enabled: boolean) => (enabled ? $.ExpensiveFeature.run() : 'fast path'),
}));

const app = App({ ExpensiveFeature });

console.log(app.run(false)); // fast path
console.log(initializationCount); // 0
console.log(app.run(true)); // expensive result
console.log(initializationCount); // 1`} />

## Defer Work, Not Ownership

If setup is expensive but only some callers need it, expose a method that performs the work on demand. Decide separately whether that method needs its own memoization:

<Editor client:load code={`import { Module } from '@favy/di';

interface Report {
  generatedAt: number;
  rows: string[];
}

const loadReport = (): Report => ({
  generatedAt: Date.now(),
  rows: ['summary'],
});

const Reports = Module()('Reports', () => ({
  load: () => loadReport(),
}));

const reports = Reports();
console.log(reports.load());`} />

## Summary

1. Keep modules focused and export their `Live` types.
2. Draw a deliberate composition root and one-way dependency flow.
3. Treat `run` as a call boundary, not an automatic web-request scope.
4. Use factory-wide caching only with an explicit reset and cleanup policy.
5. Catch errors at boundaries that can recover or add domain context.
6. Keep test state inside each fixture instance.
7. Access lazy dependencies inside the condition that needs them.
